Pulse · operator guide

Send a notification without writing the plumbing

Pulse takes one HTTP call and delivers it over email, push, SMS, an in-app inbox and webhooks — rendering the template in the right language, respecting the person's opt-outs, retrying what fails, and logging every attempt. This guide gets you from a cold machine to a delivered message.

One time

Start it up

Three processes: Docker for the local AWS stand-ins, the API, and the delivery workers. You need Node 24, pnpm 11 and Docker running.

# from ~/Desktop/pulse
docker compose up -d   # DynamoDB :8102 · queues :9324 · MailHog :8125
pnpm install
pnpm build
pnpm seed              # demo tenant, API key, two templates
pnpm dev               # API on :3100 + workers, together

Then open localhost:3100/console. The dot next to the wordmark turns green when the API is healthy.

The one that catches people

pnpm dev runs two things. The API accepts your message; the workers are what actually send it. If a message sits at queued and never moves, the workers aren't running.

Two minutes

Your first send

The demo seed already gave you a tenant, a key, a subscriber and two templates, so you can skip straight to sending.

  1. Open the console and claim a key

    Go to localhost:3100/console and press Use demo key. It's stored in your browser, so you only do this once.

  2. Pick who it's going to

    On the Send tab, leave Recipient by on Subscriber ID and paste the demo one:

    sub_demo000000000000000000

  3. Pick what to say

    Choose order-shipped from the template list. Leave the channel chips unselected — Pulse will use every channel that template defines. Leave the data box as it is.

  4. Send

    You get a message ID immediately and the status queued. That means accepted, not delivered — the queues take it from here.

  5. Watch it land

    After about two seconds the panel refreshes with a row per channel. Then open MailHog to read the email that actually left the building, and check the Inbox tab for the in-app row.

The mental model

How it thinks

Four nouns. Once these click, the rest of the API is obvious.

Tenant — one per project

ShareDeal Social is a tenant. DevAdda is another. Each gets its own templates, subscribers, quota and delivery log, and cannot see the others'. You create tenants with the admin token, not with an API key.

API key — how a project authenticates

Sent as Authorization: Bearer pk_live_…. Only a hash is stored, so the key is shown exactly once when you create it and can never be recovered — if you lose it, issue a new one and revoke the old.

Subscriber — a person who receives things

Holds their email, phone, language, device tokens and opt-outs. The important field is externalId: your own user ID. Set it once, then address people by the ID your database already uses and never store a Pulse ID anywhere.

// address by your ID, not ours
{ "to": { "externalId": "sd-user-8821" } }

Template — what to say, on every channel, in every language

One document holds the email, the push, the SMS and the in-app version — in both English and Bengali. You send data; the template decides wording.

The payoff

Because the template holds all channels, your app never decides how to notify anyone. Change a template and every future message changes — no deploy.

The five channels

emailpushsms inappwebhook
ChannelNeedsDelivered by
emailAn email address on the subscriberAWS SES, or any SMTP server
pushAt least one registered device tokenFirebase — covers Android, iOS and web
smsA phone numberBulkSMS BD, or AWS SNS
inappNothing — just the subscriberPulse itself; your app reads the feed
webhookA registered endpoint URLA signed HTTPS POST to you

You rarely name channels. Omit them and Pulse uses every one the template defines and the person can actually receive on.

Writing content

Templates

A template is JSON: one block per language, one entry per channel. Text is Liquid — {{ order.id }} pulls from the data you send.

{
  "key": "group-filled",
  "name": "Group buy filled",
  "locales": {
    "en": {
      "email": { "subject": "Your group for {{ product.name }} is complete",
                  "html": "<p>Hi {{ subscriber.name }}, filled at ৳{{ product.price }}.</p>" },
      "push":  { "title": "Group filled!", "body": "{{ product.name }} — ৳{{ product.price }}" },
      "sms":   { "text": "Your group for {{ product.name }} is complete." },
      "inapp": { "title": "Group filled", "body": "{{ product.name }}",
                  "deeplink": "/groups/{{ group.id }}" }
    },
    "bn": {
      "email": { "subject": "{{ product.name }} এর গ্রুপ সম্পূর্ণ হয়েছে", "html": "…" },
      "push":  { "title": "গ্রুপ পূর্ণ!", "body": "{{ product.name }}" }
    }
  }
}

Three rules worth knowing

  • English is the fallback. locales.en is required. Above, Bengali has no sms — so a Bengali speaker still gets the English SMS rather than no SMS at all.
  • Missing channel means skipped, not broken. That template has no webhook. Ask for webhook anyway and it comes back skipped while everything else delivers.
  • Editing publishes a new version. Old versions stay readable, and a message already accepted keeps the wording it was accepted with — an edit can never rewrite something already in flight.
Language

You don't pass a language. It comes from the subscriber's locale, so a Bengali user gets Bengali automatically. Pass locale on the send only when you need to override that.

Interpreting

Reading results

Each channel settles independently, then those roll up into one status for the message. The distinction that matters: not everything that didn't send is a failure.

Per channel

StatusWhat happenedDo you act?
deliveredThe provider accepted itNo
suppressedThey opted out, or the address hard-bounced before. Deliberately not sentNo — this is correct behaviour
skippedNothing to send on — no phone number, no device, no template bodyOnly if you expected them to be reachable
failedThe provider rejected it after retriesYes — read the error

The whole message

StatusMeans
queuedAccepted, on its way to the workers
scheduledWaiting for its send time. Still cancellable
processingSome channels have reported, others haven't
deliveredNothing failed
partialSome channels landed, some failed
failedEvery channel failed
cancelledYou cancelled it before it went
Worth internalising

A message where every channel was suppressed reports delivered. Pulse did exactly what the person's preferences asked for — that's success, not failure.

Integration

From your code

The console is for operating and debugging. Your app makes one HTTP call.

NestJS — a service you write once

@Injectable()
export class PulseService {
  private readonly base = process.env.PULSE_URL!;
  private readonly key  = process.env.PULSE_API_KEY!;

  async notify(input: {
    userId: string;
    templateKey: string;
    data: Record<string, unknown>;
    channels?: string[];
    idempotencyKey?: string;
  }) {
    const res = await fetch(`${this.base}/v1/notifications`, {
      method: 'POST',
      headers: {
        authorization: `Bearer ${this.key}`,
        'content-type': 'application/json',
        // reuse your own event id — retries then can't double-send
        ...(input.idempotencyKey ? { 'idempotency-key': input.idempotencyKey } : {}),
      },
      body: JSON.stringify({
        to: { externalId: input.userId },
        templateKey: input.templateKey,
        channels: input.channels,
        data: input.data,
      }),
    });
    if (!res.ok) throw new Error(`pulse ${res.status}: ${await res.text()}`);
    return res.json();
  }
}

Then every call site is one line:

await this.pulse.notify({
  userId: buyer.id,
  templateKey: 'group-filled',
  data: { product, group },
  idempotencyKey: `group-${group.id}-filled`,
});

Flutter — two things to wire

// 1 — on login, register the device so push can reach them
await dio.post('/v1/subscribers/$subscriberId/devices', data: {
  'token': await FirebaseMessaging.instance.getToken(),
  'platform': Platform.isIOS ? 'ios' : 'android',
});

// 2 — the notification bell
final res = await dio.get('/v1/inbox',
    queryParameters: {'subscriberId': subscriberId});

res.data['unreadCount'];  // the badge
res.data['data'];         // title, body, deeplink, readAt — newest first

await dio.post('/v1/inbox/$itemId/read',
    queryParameters: {'subscriberId': subscriberId});

curl — the shape of every call

curl -X POST localhost:3100/v1/notifications \
  -H "Authorization: Bearer $KEY" \
  -H 'content-type: application/json' \
  -H 'Idempotency-Key: group-9931-filled' \
  -d '{
    "to": { "externalId": "sd-user-8821" },
    "templateKey": "group-filled",
    "data": { "product": { "name": "Basmati Rice 5kg", "price": 620 },
              "group": { "id": "9931" } }
  }'
Always send an Idempotency-Key

Use an ID from your own domain — group-9931-filled, order-1001-shipped. Retry the same call and Pulse returns the original result and sends nothing. Without it, a retried webhook or a double-tap sends twice.

Recipes

A one-time passcode

Force SMS only — never let an OTP fan out to email.

{ "to": { "externalId": "sd-user-8821" },
  "templateKey": "otp",
  "channels": ["sms"],
  "data": { "code": "4821" } }

An order update, everywhere at once

No channels, so it uses everything the template defines and the person accepts.

{ "to": { "externalId": "sd-user-8821" },
  "templateKey": "order-shipped",
  "data": { "order": { "id": "A-1001", "eta": "Sunday" } } }

A reminder for later

Cancel any time before it fires with POST /v1/notifications/{id}/cancel.

{ "to": { "externalId": "sd-user-8821" },
  "templateKey": "cart-reminder",
  "sendAt": "2026-08-03T09:00:00Z" }

Everyone on a topic

POST /v1/topics/dhaka-buyers/broadcast
Idempotency-Key: launch-announce-v1

{ "templateKey": "new-feature", "channels": ["inapp", "push"] }

A one-off with no template

For things not worth storing. Note to.email — no subscriber needed.

{ "to": { "email": "someone@example.com" },
  "channels": ["email"],
  "content": { "email": { "subject": "Your invoice",
                        "html": "<p>Attached.</p>" } } }

Staying welcome

Opt-outs & bounces

Someone unsubscribes

One call. Every future send skips that channel for them automatically — you never add a check anywhere in your code.

POST /v1/subscribers/{id}/unsubscribe
{ "channel": "email" }

Finer control by topic — marketing off, receipts on:

PUT /v1/subscribers/{id}/preferences
{ "categories": { "marketing": false, "transactional": true } }

An address goes bad

When a mailbox permanently rejects mail, or someone hits "spam", AWS tells Pulse and the address is added to a suppression list. Every later send to it comes back suppressed without touching the provider.

Why this isn't optional

AWS measures your bounce and complaint rates. Cross roughly 5% bounces or 0.1% complaints and they throttle or suspend your ability to send email at all. The suppression list is what protects that — leave it on.

Temporary problems — a full mailbox, a DNS blip — are deliberately not suppressed. Those clear up, and cutting someone off permanently over an afternoon would be wrong.

Diagnosing

When it breaks

Errors always come back the same shape. Read the code — that's the stable part.

{ "error": { "code": "TEMPLATE_NOT_FOUND", "message": "no template 'welcome'" } }
You seeIt meansFix
Stuck on queuedNothing is draining the queueThe workers aren't running — pnpm dev
INVALID_API_KEYKey unknown, or you re-seededPress Use demo key again
TEMPLATE_NOT_FOUNDNo template by that key for this tenantCheck the Templates tab — keys are case-sensitive
VALIDATION_FAILEDBad request bodydetails lists exactly which fields
QUOTA_EXCEEDEDMonthly plan limit hitRaise the tenant's quota
SCHEDULE_IN_PASTsendAt already passedSend a future time, or drop the field to send now
Channel is skippedNo destination or no template bodyCheck the person has a phone/device, and the template covers that channel
No email in MailHogIt never got that farOpen the message in the Delivery log — the per-channel error is there

The Delivery log is the tool for this. Click any message to see each channel's outcome, the exact content that was rendered, and every delivery attempt with its provider error.

Before real users

Going live

Everything so far runs on your laptop against local stand-ins. Two independent tracks get you to production — you don't have to do them in order.

Email, this afternoon

Point EMAIL_PROVIDER=smtp at any real SMTP host — Postmark, Resend, Brevo. Real email, no AWS, no waiting.

Email on SES, in a few days

Cheaper at volume ($0.10 per thousand), but you must verify a domain and ask AWS to lift the sandbox — usually 24–48 hours.

The checklist

  • Deploy — cdk deploy -c env=dev first; dev sends nothing, so it's a safe way to shake out permissions.
  • A real admin token — 32+ random characters. The API refuses to start in production without one.
  • Email — an SMTP provider, or a verified SES domain with SPF, DKIM and DMARC set up.
  • Push — a Firebase project and its service-account JSON. One credential covers Android and iOS.
  • SMS — a BulkSMS BD key. Their rate is roughly a hundredth of AWS SNS for Bangladesh, which matters enormously at volume.
  • Bounce handling — connect SES feedback to the topic the deploy created. Skip this and your sending reputation degrades silently.
  • A tenant per project — separate keys, so revoking one doesn't affect the others.
